# 測試計畫｜餐點外送系統

依據 `/doc/requirements.md`、`/doc/architecture.md`、`/doc/data-model.md`、`/doc/todo.md` 產生。測試案例依 `todo.md` 的四階段優先級排序，優先涵蓋階段一（核心下單流程）與階段四（搶單競態、即時定位）。

## 1. 測試目標與範圍

**目標**：驗證系統能滿足 `requirements.md` 的四項驗收標準——(1) 消費者完整跑完下單流程、(2) 餐廳更新狀態消費者同步查到、(3) 成功部署 Render 且對外可存取、(4) 資料重啟後仍保留。

**測試範圍**：
- 消費者／餐廳／外送員／管理員四種角色的核心功能（對應 `todo.md` 階段一～四）
- 訂單狀態機的合法/非法轉換
- 售罄檢查、搶單防重複競態等關鍵業務規則
- 模擬付款狀態流轉
- 部署後的對外可存取性與資料持久性

**不在測試範圍內**：
- 真實金流串接（系統採模擬付款，不涉及）
- 系統自動派單演算法（已確認採外送員自行搶單，非系統指派）
- 多語系、Email/簡訊/推播通知（需求文件標示不需要）
- 大規模壓力測試（超出「數百人同時在線」的效能目標範圍，見 `architecture.md` 效能考量）

## 2. 測試策略

| 測試類型 | 定位與涵蓋範圍 |
|---|---|
| 單元測試 | 訂單狀態機轉換邏輯、金額計算（購物車加總、訂單快照）、密碼雜湊等純邏輯函式 |
| 整合測試 | API 層與資料庫互動，例如建立訂單時同時寫入 `orders`/`order_items`/`payments` 是否正確、搶單時的唯一約束是否生效 |
| API 測試 | 針對 `architecture.md` 第 6 節所列所有端點，涵蓋成功/失敗/權限情境 |
| 前端元件測試 | 個別畫面元件（購物車項目列表、訂單狀態標籤、地圖元件）的呈現邏輯 |
| 端對端測試 | 完整流程：消費者下單 → 餐廳接單出餐 → 外送員搶單配送 → 消費者查看送達，對應 `requirements.md` 驗收標準 1、2 |
| 手動驗收測試 | 部署後的對外存取、Render 服務重啟後資料持久性、地圖視覺化的實際呈現效果 |

## 3. 測試環境與測試資料規則

| 項目 | 本機（SQLite） | 正式（Render PostgreSQL） |
|---|---|---|
| 資料庫初始化 | 每次測試執行前清空並重建 schema，避免資料互相污染 | 僅在部署驗收階段使用，不作為日常自動化測試環境 |
| 測試資料建立方式 | 使用測試 fixture／seed script 建立固定測試帳號（各角色至少一組）、測試餐廳與餐點 | 部署驗收時手動建立最小驗證資料集，不使用正式使用者真實資料 |
| 金流測試資料 | 一律為模擬付款，不使用任何真實卡號或金流測試帳號 | 同左 |
| 資料清理 | 自動化測試（單元/整合/API）每次執行後清空測試資料庫 | 部署驗收測試產生的測試訂單，驗收後應標記或清除，避免污染正式環境資料 |
| SQLite/PostgreSQL 差異注意事項 | `NUMERIC` 型別、唯一約束、`DATETIME` 時區處理在兩者可能有細微差異，涉及金額與搶單唯一約束的測試案例（見 4.x）應在兩種資料庫皆執行過一次 | 同左 |

## 5. API 測試重點（FastAPI）

針對 `architecture.md` 第 6 節所列每個端點，至少涵蓋：

- **成功情境**：合法輸入、合法角色，回傳預期狀態碼與資料結構
- **驗證失敗**：Pydantic schema 驗證失敗（如缺少必填欄位、型別錯誤、金額為負數），回傳 422
- **未授權**：未帶 JWT 或 JWT 失效，回傳 401
- **權限不足**：JWT 合法但角色不符（如消費者呼叫餐廳專屬 API），回傳 403
- **找不到資源**：查詢不存在的訂單/餐點/餐廳 ID，回傳 404
- **伺服器錯誤**：模擬資料庫連線異常等情境下的錯誤處理與回應格式一致性
- **狀態衝突**：訂單狀態機非法轉換、搶單競態衝突，回傳明確的業務邏輯錯誤（建議 409 Conflict）

## 6. 前端測試重點

- **畫面呈現**：各角色頁面正確依登入角色顯示對應功能（消費者看不到餐廳管理介面等）
- **使用者互動**：加入購物車、送出訂單、狀態按鈕點擊等操作皆有明確回饋（成功/失敗提示）
- **表單驗證**：註冊/登入表單、新增餐點表單的前端驗證（必填、格式）與後端驗證行為一致
- **載入／錯誤狀態**：API 呼叫中顯示載入中提示；API 失敗時顯示錯誤訊息而非空白頁面
- **輪詢與即時提醒**：訂單狀態、配送位置的輪詢機制正確運作，狀態變化時畫面即時提示（對應已確認決策「網頁內即時提醒」）
- **地圖元件**：Leaflet.js + OpenStreetMap 地圖正確顯示配送位置標記，位置更新時標記隨之移動

## 7. 資料庫測試重點

- **欄位限制**：`NOT NULL`、金額 ≥ 0、數量 ≥ 1 等約束是否在資料庫層級與應用層級皆生效
- **關聯完整性**：刪除/停用上游資料（如停權餐廳）時，既有訂單、餐點資料是否仍正確保留關聯，不因外鍵問題出錯
- **資料驗證**：`orders.status`、`payments.status` 僅允許列舉值內的字串
- **唯一約束**：`users.email`、`payments.order_id`、`delivery_assignments.order_id`、`cart_items.(cart_id, menu_item_id)` 的唯一約束是否正確攔截違規寫入（尤其 TC-4.2-02 的搶單併發測試）
- **索引有效性**：針對 `data-model.md` 第 5 節建議索引，確認查詢計畫（EXPLAIN）有使用到索引，而非全表掃描
- **SQLite/PostgreSQL 差異**：涉及 `NUMERIC` 精度與唯一約束的測試案例，建議在兩種資料庫環境各執行一次，確認行為一致

## 8. 安全性測試

- 檢查程式碼與 Git 歷史紀錄中不含任何明碼密碼、API Key、資料庫連線字串（比對 `AGENTS.md` 機密資訊管理規則）
- 檢查前端畫面（含瀏覽器開發者工具的 Network 分頁）不會回傳其他使用者的敏感資料（如他人訂單、他人配送位置）
- 驗證密碼儲存為雜湊值，資料庫中查無明碼密碼
- 驗證 JWT 過期後無法再存取需登入的 API
- 驗證角色權限矩陣：每個 API 端點僅允許 `architecture.md` 第 6 節標示的角色存取
- 驗證輸入資料的注入防護（FastAPI + Pydantic + ORM 參數化查詢預設具備，需確認未繞過 ORM 直接拼接 SQL）

## 9. 缺陷回報格式

| 欄位 | 說明 |
|---|---|
| 標題 | 簡短描述問題 |
| 重現步驟 | 逐步操作，含輸入資料 |
| 預期結果 | 應該發生什麼 |
| 實際結果 | 實際發生什麼（含錯誤訊息截圖或日誌） |
| 環境 | 本機（SQLite）／正式（Render PostgreSQL）、瀏覽器版本 |
| 對應案例編號 | 若源自本文件的測試案例，填寫案例編號 |
| 嚴重度 | 致命（阻擋核心流程）／高（影響主要功能）／中（次要功能異常）／低（外觀或文字問題） |

## 10. 測試完成標準

## 11. 待確認事項

- 一位餐廳角色使用者是否只能對應一間餐廳——若未來支援連鎖店多分店，需補充對應測試案例。
- 餐點下架的軟刪除機制尚未定案，待 `data-model.md` 該項確認後，需補充對應的測試案例（歷史訂單是否仍可正確顯示已下架餐點）。
- 購物車是否允許混合多間餐廳的餐點——若允許，需補充跨餐廳下單的拆單測試案例；若不允許，需補充「加入不同餐廳餐點時的行為」測試案例。
- 即時位置輪詢的確切秒數尚未拍板，效能測試（TC-4.3/4.4 相關）的具體壓力測試門檻待該數值確定後再補充。
- 是否需要自動化 CI 流程執行本測試計畫中的自動化案例（單元/整合/API），需求文件未提及，屬開發階段可另行決定的工具鏈選擇。
