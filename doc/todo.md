# 待辦清單｜餐點外送系統

依據 `/doc/architecture.md` 產生，依 MVP 優先順序排列：**核心下單流程（含庫存售罄檢查）→ 餐廳/管理員管理功能 → 模擬付款 → 外送員搶單與即時定位配送**。

狀態欄位：`Todo` / `In Progress` / `Done`。

## 階段一：核心下單流程（最高優先）

| # | 項目 | 相依關係 | 驗收條件 | 狀態 |
|---|---|---|---|---|
| 1.1 | 建立專案骨架（`backend/`、`frontend/` 目錄、FastAPI 基本啟動、SQLite 連線） | 無 | `uvicorn main:app --reload` 可啟動，根路徑回應成功 | Done |
| 1.2 | 實作 `users` 資料表與認證（註冊/登入、JWT 發放） | 1.1 | 消費者／餐廳／外送員可公開註冊登入；管理員不可自助註冊，但預先建立的管理員可登入；密碼以雜湊儲存 | Done |
| 1.3 | 實作餐廳與菜單管理 API（`restaurants`、`menu_categories`、`menu_items`，含 `is_sold_out`） | 1.2 | 餐廳可新增/修改/下架餐點；`is_sold_out=true` 的餐點可被查到但標示售罄 | Done |
| 1.4 | 消費者瀏覽餐廳與餐點 API | 1.3 | `GET /restaurants`、`GET /restaurants/{id}/menu` 回傳正確資料 | Done |
| 1.5 | 購物車 API（`carts`、`cart_items`） | 1.4 | 消費者可加入/修改/刪除購物車項目；加入售罄餐點應被拒絕 | Done |
| 1.6 | 建立訂單 API（`POST /orders`，含價格快照、售罄檢查、模擬付款） | 1.5 | 建立訂單後，售罄餐點無法下單；訂單總金額與明細正確；`payments.status` 自動設為 `paid` | Done |

| 1.9 | 前端：餐廳頁面（菜單管理、訂單列表、狀態更新） | 1.3, 1.7 | 餐廳能接單並更新狀態，消費者端輪詢後同步看到（對應 requirements.md 驗收標準 2） | Done |

## 等待確認（不可直接開發，需先釐清才能轉為正式待辦）

以下項目對應 `requirements.md`／`architecture.md`／`data-model.md` 的待確認事項，**在確認前不得視為可開發項目**：

- 一位餐廳角色使用者是否只能對應一間餐廳（連鎖店多分店支援）——影響 `restaurants` 與 `users` 的關聯設計，若要支援需重新設計階段一的 1.3。
- 餐點下架是否需要軟刪除機制（`menu_items.is_active`）——建議方向已記錄於 `data-model.md`，但尚未經使用者最終確認，暫不視為定案。
- 購物車是否允許混合多間餐廳的餐點——影響階段一 1.5、1.6 的下單邏輯是否需要拆單，需先確認才能寫入詳細規格。
- 是否需要多語系支援——未涵蓋於任何階段，如需要需重新評估前端頁面設計。
- 即時位置追蹤輪詢的確切秒數——目前 4.3/4.6 先以 architecture.md 建議的 5-10 秒作為開發預設值，非最終定案，效能測試後可能調整。
