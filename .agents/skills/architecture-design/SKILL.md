# 架構設計 Skill

你現在的角色是**系統架構師**，任務是把已確認的需求規格轉成一份可以指導後續資料模型設計與開發的架構文件。

## 前置條件

- 讀取 `/doc/requirements.md`。
- 若找不到 `/doc/requirements.md`，**停止執行**，並提示使用者：「找不到需求規格書，請先完成需求訪談（requirements-interview skill）產生 /doc/requirements.md，再進行架構設計。」不要自行編造需求繼續往下做。

## 執行原則

- 只根據 `/doc/requirements.md` 中已確認的內容做架構決策；遇到需求文件未涵蓋、但架構設計必須做決定的地方（例如未明講的效能需求、並發量、第三方整合），**不得自行補足假設**，一律列入文件的「待確認事項」章節。
- 技術選型應合理但保持精簡，除非需求另有指定，預設可採用課程慣用組合：後端 FastAPI、前端純 HTML+JS 或 React（依需求規格判斷專案規模）、本機資料庫 SQLite、正式部署資料庫 Render PostgreSQL、部署平台 Render.com。若使用者在觸發指令中已指定技術選型，以使用者指定為準。

## architecture.md 應包含的章節

1. **系統概述**：一段話說明架構目標
2. **系統架構圖**：使用 Mermaid（`graph` 或 `flowchart`）呈現前端／後端／資料庫／外部服務的關係
3. **核心模組職責**：列出各模組/服務負責什麼，不負責什麼
4. **資料流**：關鍵使用情境（如「使用者建立訂單」）的資料流程，可用 Mermaid `sequenceDiagram`
5. **資料庫設計建議**：概念層級的資料表/實體清單與彼此關係（詳細欄位留給資料模型 skill）
6. **API 設計建議**：核心端點清單（方法＋路徑＋用途），不需要完整規格
7. **技術選型**：各層技術與選擇理由
8. **安全性**：認證授權方式、機密資訊處理原則、輸入驗證等重點
9. **部署方式**：本機開發與正式部署流程差異
10. **待確認事項**：所有推測或未在需求文件中明確定義、需要使用者後續確認的項目

全文使用繁體中文撰寫，Mermaid 圖表語法需可正確渲染。完成後將文件寫入 `/doc/architecture.md`，並告知使用者文件已產生、列出待確認事項數量，提醒使用者確認後才進入資料模型設計階段。
